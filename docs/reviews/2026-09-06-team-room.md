Supplement to the [general review](2026-09-06.md), against the same production

## Most consequential additional findings

### T01 — P1: Parked posts are typed together, but only the last is tracked

**Reproduced with the real TeamController and a fake host.** While a bot is busy,
post two messages. When it becomes free, `FlushParked` iterates every queued line
and calls `TypeToClaude` immediately for each. `Expect` stores just one
`_submits[sessionId]`, replacing the previous submission.

Probe result: **two messages typed before any ACK, one tracked submission**.
The real AppController writes each text immediately and schedules its Enter
400 ms later. The messages can concatenate in the composer before either Enter,
and the first message loses its independent confirmation/retry state.

Source: `TeamController.cs:1382–1435`, `AppController.cs:2750–2784`.
Use a per-bot FIFO with one in-flight submission; release the next item only after
the current item is acknowledged or reaches an explicit terminal outcome.

### T02 — P1: An old acknowledgement can confirm a different post

**Reproduced.** `OnAgentStatus` treats any Working status whose detail begins
`[Perch team]` as confirmation of whichever submission is currently tracked.
Although DeliveryLine includes the room sequence, the ACK path does not compare
it. Send A, then B before A's hook arrives; A's acknowledgement removes B.

Probe result: **zero submissions tracked after acknowledging A, although B was
the pending submission**. The same broad echo also sets `Wrap.Confirmed`, so
wrap/reset correctness depends on solving correlation too.

Source: `TeamController.cs:1346–1369`. Correlate an immutable delivery ID with
project, recipient, session generation, and message. Do not infer confirmation
from a shared text prefix. Add late, duplicate, out-of-order, and previous-session
ACK scenarios alongside the FIFO tests.

### T03 — P1: Same-named bots in different projects share startup queues

**Queue collision reproduced; wrong-recipient delivery follows from the drain
path but was not sent to a real agent.** `_pendingStart` and `_startingBots` are
keyed only by `bot.Slug`, while nickname/slug uniqueness is per team. During a
slow start for project A's `ada`, a post to project B's `ada` joins A's queue and
does not initiate B's start. A's completion drains the shared queue into A's
session, including the other project's post and its unrelated sequence number.

Probe result: **two projects, one start, one queue containing both posts**.
Globally minted Claude peer names do not prevent this; these maps use Slug, not
CcName. Other slug-keyed state, including model fallback/debounce and unclaimed
work warnings, also needs review for cross-project interference.

Source: `TeamController.cs:114–117`, `2663–2669`, `2485–2500`.
Key every project-local bot operation by `(projectId, botSlug)`. Centralize startup
deduplication: manual `OnBotStartAsync` currently bypasses the delivery start guard,
so concurrent starts also need one shared in-flight operation per bot.

### T04 — P1: Unreadable task data is silently overwritten

**Reproduced.** `TeamStore.Readable` protects team.json, but `LoadTasks` catches a
tasks.json parse failure and returns a new empty TaskDoc. `SaveTasks` checks only
the team's Readable flag and writes that empty document over the broken task file.

Probe result: **original malformed task content lost, team Readable still true**.
This can turn a temporary partial external edit or merge conflict into permanent
loss of the task board. `TasksChangedOnDisk` also treats a deleted task file as
unchanged, so cached tasks can be written back after deletion.

Source: `TeamStore.cs:105–159`. Track task readability separately; preserve the
last good state and original bytes on parse failure, surface the problem, and
refuse writes until it is resolved. Detect deletion explicitly. Avoid rereading
and replacing the mutated task object inside SaveTasks after an external change;
use a versioned snapshot and conflict handling for concurrent edits.

### T05 — P1/P2: “Send again” bypasses normal delivery gates and drops images

**Busy bypass and attachment loss reproduced.** `OnDeliverRetry` has a separate
delivery path. For an existing session it wakes/starts the bot, then can immediately
type without the normal cold-start, Working, or wrap/reset gates. It also rebuilds
the line from `post.Text` without `WithImage(post.Text, post.Image)` in either
the existing-session or missing-session branch.

Probe result: **one line typed into a Working bot; original attachment absent**.
For a waking/restored session the source path additionally allows text to reach
a booting shell rather than waiting for Claude, repeating the class of bug the
normal delivery code carefully avoids. Image-only posts lose their payload.

Source: `TeamController.cs:2290–2335`. Route retries through the same queue and
startup gates as first delivery, preserve the complete payload, and deduplicate
pending `(post, recipient)` retries. Test busy, dormant, unspawned, resetting,
image-only, and double-click retry cases with delayed host callbacks.

### T06 — P1: Permission fallback sends terminal keys without verifying the prompt

**Source-confirmed; no real permission was answered in this review.** After a
room Allow/Deny, a three-second fallback writes Enter/Escape if an in-memory
marker remains. `AnswerPromptOnScreen` does not inspect the terminal, validate
the original request ID, or verify that the same session generation and prompt
still exist. Any Working/Done hook clears the marker, but a delayed/missing hook
does not prove that the original permission prompt is still on screen.

Source: `TeamController.cs:1094–1135`, `1155–1170`.
An answer can therefore affect a later prompt or input buffer. Keep permission
answers tied to the exact request; use terminal fallback only with positive
identification of that same prompt. If identity cannot be established, show the
terminal to the owner. Validate ownership and request liveness before writing
the answer file as well; the current handler writes before checking the pending
request and can still log an answer for an expired card.

### T07 — P2: “Delivered” is recorded before acknowledgement and loses recipient detail

**Source-confirmed.** Initial posts set Delivered from `Attempted.Ok`, which means
the text was typed. FlushParked emits a delivered event immediately after typing.
Neither waits for the prompt-submit ACK. The web `landedSet` tracks only a post
sequence: one delivered event makes a broadcast post stop saying “waiting for the
bot,” even if another recipient remains parked or failed.

Sources: `TeamController.cs:1407/1716`, `src/web/src/team.ts:471–477`,
`src/web/src/team-room.ts:1791`.
Track recipient outcomes separately: queued, starting, submitted, acknowledged,
failed. Derive an aggregate such as “2 of 3 received; Bo still starting.” This
also makes retries target only the recipients that need them.

### T08 — P2: Pending delivery is not durable across restart or close

**Source-confirmed.** `_parked`, `_pendingStart`, `_submits`, and `_held` exist only
in memory. The ledger contains posts and status rows, but controller initialization
does not reconstruct a pending outbox from them. `OnSessionClosed` removes pending
items without recording a failure for each. A persistent “waiting” room row can
therefore outlive the only work item capable of delivering it.

Sources: TeamController dictionary declarations, constructor, StoreFor, and
`OnSessionClosed:1594–1606`. Persist per-recipient outbox state with the message;
on restart classify ambiguous submissions as uncertain, not automatically safe to
retype. Require an explicit resend or an idempotent agent-side protocol for that
case. Use ClientId as an idempotency key: it is currently echoed for optimistic
UI reconciliation but not checked for duplicate incoming posts.

## Team-room resource opportunities

- `OnRequest` returns incremental entries, but `RoomLedger.ReadSince` reads and
  deserializes the entire ledger first. Repeated requests with no new entries
  still do the full scan. Maintain an offset/index or bounded parsed cache with
  rotation detection; measure time and allocations as the room approaches its cap.
- `IngestTranscripts` reads every available bot transcript on room requests, and
  initial ingestion scans the ledger separately for each bot. Compute per-bot
  watermarks once and avoid revisiting unchanged transcripts. Keep work off the
  state thread without introducing concurrent mutation of reader state.
- `ProjectTeamView`, called during general state projection, rereads each
  position's brief and includes up to 16 KiB of it. Cache/version team definitions
  separately from rapidly changing presence/task state.
- RoomLedger's 2 MiB limit is a rotation trigger, not a hard bound: it retains
  2,000 lines regardless of their length, and does not rotate at all when there
  are at most 2,000. Long posts can keep it well above 2 MiB and cause repeated
  full rewrites. Bound bytes as well as lines without deleting active workflow
  records needed for delivery, permissions, or task recovery.

These are structural opportunities, not measured CPU/memory savings. The five
functional probes below exercised the controller/stores, not native rendering.

## Recommended implementation sequence

Fix task-file preservation and project-scoped identity first. Then implement one
delivery outbox shared by ordinary posts, retries, reactions, and wrap-up messages,
with per-recipient IDs and one in-flight submission per bot. Replace optimistic
“delivered” claims with acknowledged outcomes. Address permission correlation
independently before testing any real approval fallback.

The existing one-post warm/cold delivery gate is valuable but insufficient for
these cases. Expand it with two posts queued during a turn, identical bot names
across projects, late ACKs, retry during startup, images, restart during delivery,
and stale permission cards. Preserve the original gate rather than weakening it
to accommodate the new state machine.
